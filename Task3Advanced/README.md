#### Компонент: Витрина данных (Self-Service Portal)

- Security Layer: Отвечает за маскирование данных на лету (Row/Column Level Security). Медицинские ID заменяются суррогатными ключами, поля диагнозов исключаются на уровне view.
- Semantic Layer (Cube.js / dbt Metrics Server): Трансформирует сырые Iceberg-таблицы в бизнес-метрики (ARPU, Lifetime Value пациента, нагрузка на врача).
- Report Builder (Metabase / Superset Embedded): Open-source инструмент, встроенный в портал.

#### Компонент: Шлюз доменных событий

- Anti-Corruption Layer (ACL): Прослойка на Python/Go, которая преобразует старые Camel-сообщения из легаси в современную Event-driven модель (JSON Schema) и наоборот. Нужна на период миграции.
- Dead Letter Queue (DLQ) Processor: Компонент, который перехватывает "битые" события из Kafka и позволяет перезапустить их после исправления схемы.

## План управления рисками

### Архитектурные риски

#### Потеря консистентности (SLA данных)

##### Техническое решение:

Внедрение паттерна Transactional Outbox для критичных банковских операций (сначала запись в БД, потом ивент). Использование Idempotency Keys во всех микросервисах.

##### Управленческое:

Принимаем Eventual Consistency как норму для аналитики. Транзакционная строгость остается только в Core-системах (FinTech).

#### Сложность федеративных запросов

##### Техническое решение:

Внедрение Data Vault 2.0 на уровне Data Lakehouse. dbt строит "широкие" витрины (One Big Table) по ночам, чтобы утром аналитики не лезли напрямую в сырые таблицы.

### Организационные риски

#### Сопротивление доменов (Data Sovereignty vs Data Mesh)

##### Управленческое решение:

Создание роли Data Product Owner в каждом домене. Домен владеет данными и предоставляет их как продукт через API или поток. Внедрение четкого Data Contract между доменами. "Портит данные тот, кто их создал".

##### Техническое:

Внедрение разграничения доступа (ходы в секцию "финансы" возможны только при наличии ролей "FinTech Reader" и "Auditor" одновременно).

#### Bus Factor легаси (риск потери знаний)

##### Управленческое:

Немедленный старт программы "Reverse Engineering". Платим премию текущим сопровождающим за документирование логики всех триггеров и хранимок.

##### Техническое:

Инструменты автоматического документирования (например, написание парсером структуры DWH в Markdown).

### Технологические риски

#### Регуляторная утечка (Compliance)

##### Техническое:

Использование Differential Privacy или жесткого скрипта маскирования на уровне Ingestion Layer. Все полные ФИО и даты рождения заменяются токенами до попадания в Data Lake. Добавление автоматического теста в CI/CD, запрещающего мерж кода, если в JSON-схеме Kafka найдено поле "diagnosis_text".

#### Производительность витрины

##### Техническое:

Лимиты на панели Self-Service (лимит по времени запроса — 5 минут, лимит по объему данных на страницу). Если запрос падает — система настойчиво предлагает скачать агрегированный датасет или перейти на витрину, построенную инженерами.

##### Управленческое:

SLA на запросы в витрине жестко не фиксируем на этапе MVP, указывая, что сложные кросс-доменные запросы могут выполняться дольше обычных.

#### Миграция легаси затянется из-за скрытых зависимостей

##### Техническое:

Провести аудит зависимостей до начала миграции

##### Управленческое:

Включить задачу в этап Reverse Engineering
